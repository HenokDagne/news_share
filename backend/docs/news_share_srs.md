## 1. Introduction

### 1.1 Purpose

This document specifies the requirements for the News Share backend: a NestJS REST API that lets users register, publish news posts with images, follow other users, and receive notifications. It is the reference for designers, developers, testers and AI coding agents implementing the system.

### 1.2 Scope

The backend provides:

- Account registration, login, token refresh and logout.
- User profiles with avatars.
- Posts with optional images, a personal feed and a global timeline.
- A follow graph (follow, unfollow, follower lists).
- In-app notifications generated by follow and new-post events.
- Image storage on Cloudinary; relational data on local PostgreSQL via Prisma.
- Interactive API documentation with Swagger.

The backend replaces the existing Supabase implementation. The Flutter mobile app is the primary client and is out of scope except for the API contract it consumes.

See section 14.

## 2. Overall description

### 2.1 Product perspective

```
┌────────────────┐   HTTPS / JSON      ┌──────────────────────┐
│ Flutter app    │ ──────────────────▶ │ NestJS REST API      │
│ (client)       │ ◀────────────────── │ /api/v1, Swagger     │
└───────┬────────┘                     └─────┬──────────┬─────┘
        │                                    │          │
        │ loads images by URL                │ Prisma   │ SDK upload/delete
        ▼                                    ▼          ▼
┌────────────────┐                     ┌──────────┐ ┌────────────┐
│ Cloudinary CDN │ ◀────────────────── │PostgreSQL│ │ Cloudinary │
└────────────────┘   (same service)    │ (local)  │ │ (storage)  │
                                       └──────────┘ └────────────┘
```

### 2.2 User classes

| Class | Description |
|---|---|
| Anonymous visitor | Can only register, log in and refresh tokens |
| Registered user | Can manage their profile, create and manage their own posts, follow users, read posts and notifications |
| Developer / operator | Runs the server, database and migrations; reads API docs |

There is no admin role in version 1.

### 2.3 Operating environment

- Node.js 20 or newer.
- PostgreSQL 16 running locally (Docker Compose for development).
- Outbound internet access to Cloudinary.
- Clients: Flutter app on Android and iOS, plus any HTTP client.

### 2.4 Design and implementation constraints

- Backend framework: NestJS with TypeScript.
- ORM: Prisma 6. No raw SQL for application logic.
- Database: local PostgreSQL (no hosted Supabase database).
- Images are stored on Cloudinary only. The database stores the image URL and public ID, never image bytes.
- Authentication is implemented by the backend (JWT + rotating refresh tokens).
- Authorization rules are enforced in NestJS services (no row-level security).

### 2.5 Assumptions and dependencies

- A Cloudinary account (cloud name, API key, API secret) is available.
- Existing Supabase data can be exported (users with bcrypt hashes, profiles, posts, followers, notifications).
- The mobile client can store tokens securely and send an `Authorization` header.

## 3. System architecture

### 3.1 Layered design

| Layer | Responsibility | Location |
|---|---|---|
| Controllers | HTTP routing, request parsing, Swagger metadata | `src/*/*.controller.ts` |
| DTOs | Input validation and documentation | `src/*/dto/` |
| Services | Business rules, authorization, orchestration | `src/*/*.service.ts` |
| Data access | Prisma client | `src/prisma/` |
| Storage | Cloudinary upload and delete | `src/storage/` |
| Events and listeners | Decoupled side effects (notifications) | `src/common/events/`, `src/notifications/listeners/` |
| Cross-cutting | Auth guard, exception filter, pagination, config | `src/common/`, `src/config/` |

### 3.2 Modules

| Module | Purpose |
|---|---|
| `AuthModule` | Register, login, refresh, logout, JWT strategy |
| `UsersModule` | Profiles, avatar, user search |
| `PostsModule` | Posts, feed, timeline, owner-only edit and delete |
| `FollowsModule` | Follow graph and counters |
| `NotificationsModule` | Notification API and event listeners |
| `StorageModule` (global) | Cloudinary access |
| `PrismaModule` (global) | Database access |

### 3.3 Key flows

**Image upload and display**

```
Upload:   Flutter --multipart--> NestJS --upload_stream--> Cloudinary
                                   |<-- secure_url + public_id
                                   v
                              PostgreSQL stores image_url + image_public_id

Display:  Flutter --GET /feed--> NestJS --> PostgreSQL --> JSON with imageUrl
          Flutter --GET imageUrl--> Cloudinary CDN (bytes never pass through NestJS)
```

**Event-driven notifications**

```
FollowsService.follow()  --emit user.followed-->  NotificationListener --> notifications row
PostsService.create()    --emit post.created--->  NotificationListener --> one row per follower
```

### 4.1 Structure conventions

- One folder per feature module (controller, service, DTOs, module).
- DTO files end in `.dto.ts` so the Swagger CLI plugin documents them automatically.
- Controllers contain no business logic; services contain no HTTP concerns.
- Only `notification.listener.ts` creates notifications.
- Only `StorageService` talks to Cloudinary.
- Only `PrismaService` talks to the database.
- Shared code lives in `common/`; never import one feature module's internals from another (shared pieces go in `common/` or `users.mapper.ts`).

## 5. Functional requirements

Priority: **M** = must have, **S** = should have. Each requirement has a testable outcome in section 11.

### 5.1 Authentication (FR-AUTH)

| ID | Requirement | Priority |
|---|---|---|
| FR-AUTH-01 | The system shall let an anonymous visitor register with email, password, username and optional full name. Registration shall create the login identity and the profile atomically. | M |
| FR-AUTH-02 | The system shall reject registration when the email or username is already used (username compared case-insensitively) with `409`. | M |
| FR-AUTH-03 | The system shall validate: email format, password 8 to 72 characters, username `^[a-zA-Z0-9_]{3,20}$`. | M |
| FR-AUTH-04 | The system shall store passwords only as argon2id hashes and never return them. | M |
| FR-AUTH-05 | The system shall authenticate users by email and password and return an access token (15 minutes) and a refresh token (30 days). | M |
| FR-AUTH-06 | Invalid credentials shall return `401` with the same message whether the email or the password was wrong. | M |
| FR-AUTH-07 | The system shall exchange a valid refresh token for a new token pair and revoke the used token (rotation). A used, expired or unknown refresh token shall return `401`. | M |
| FR-AUTH-08 | The system shall store refresh tokens only as hashes. | M |
| FR-AUTH-09 | The system shall let a logged-in user revoke a refresh token (logout). | M |
| FR-AUTH-10 | The system shall accept legacy bcrypt hashes imported from Supabase and re-hash them to argon2id after a successful login. | M |
| FR-AUTH-11 | Every endpoint except register, login and refresh shall require a valid access token (`401` otherwise). | M |
| FR-AUTH-12 | Register and login shall be rate limited to 10 requests per minute per client. | S |

### 5.2 Profiles and avatars (FR-USER)

| ID | Requirement | Priority |
|---|---|---|
| FR-USER-01 | A user shall be able to read their own profile including email. | M |
| FR-USER-02 | A user shall be able to update their username, full name and bio. A taken username shall return `409`. | M |
| FR-USER-03 | A user shall be able to read any profile by id; the response shall not include email. | M |
| FR-USER-04 | A user shall be able to search profiles by username or full name (case-insensitive substring) with cursor pagination. | M |
| FR-USER-05 | A user shall be able to upload or replace their avatar (JPEG, PNG or WebP, max 2 MB). The image is stored on Cloudinary and the profile stores its URL and public ID. | M |
| FR-USER-06 | A user shall be able to remove their avatar; the Cloudinary asset shall be deleted. | M |
| FR-USER-07 | Profile responses shall include `followersCount` and `followingCount`. | M |

### 5.3 Posts (FR-POST)

| ID | Requirement | Priority |
|---|---|---|
| FR-POST-01 | A user shall be able to create a post with a title, content and/or an image. A post with none of the three shall be rejected with `400`. | M |
| FR-POST-02 | Post titles shall be at most 150 characters; content at most 5000. | M |
| FR-POST-03 | A post image (JPEG, PNG or WebP, max 5 MB) shall be uploaded to Cloudinary; the database shall store its URL and public ID; the API shall return only the URL as `imageUrl`. | M |
| FR-POST-04 | If saving the post fails after a successful upload, the uploaded image shall be deleted. | M |
| FR-POST-05 | A user shall be able to read any post by id. | M |
| FR-POST-06 | The system shall provide a personal feed: posts from followed users plus the user's own, newest first, cursor-paginated. | M |
| FR-POST-07 | The system shall provide a global timeline, newest first, cursor-paginated. | M |
| FR-POST-08 | The system shall list the posts of a given user, newest first, cursor-paginated. | M |
| FR-POST-09 | Only the author shall be able to update a post (`403` otherwise). Uploading a new image shall replace and delete the old Cloudinary asset. An update that would leave the post empty shall be rejected. | M |
| FR-POST-10 | Only the author shall be able to delete a post (`403` otherwise). Deleting removes the row, its notifications, and the Cloudinary image. | M |
| FR-POST-11 | Each post response shall embed the author's id, username, full name and avatar URL. | M |

### 5.4 Follows (FR-FOLLOW)

| ID | Requirement | Priority |
|---|---|---|
| FR-FOLLOW-01 | A user shall be able to follow another user. Following oneself shall return `400`; following an unknown user shall return `404`. | M |
| FR-FOLLOW-02 | Following is idempotent: repeating a follow succeeds and changes nothing. | M |
| FR-FOLLOW-03 | A new follow shall increment the follower's `followingCount` and the target's `followersCount` in one transaction. | M |
| FR-FOLLOW-04 | A user shall be able to unfollow; unfollowing is idempotent and decrements both counters only if a follow existed. | M |
| FR-FOLLOW-05 | The system shall report whether the current user follows, and is followed by, another user. | M |
| FR-FOLLOW-06 | The system shall list a user's followers and the users they follow, newest first, cursor-paginated. | M |
| FR-FOLLOW-07 | A new follow (not a repeat) shall create exactly one `follow` notification for the target. Unfollowing shall create none. | M |

### 5.5 Notifications (FR-NOTIF)

| ID | Requirement | Priority |
|---|---|---|
| FR-NOTIF-01 | Notifications shall be created only by the server, never by clients. | M |
| FR-NOTIF-02 | When a user creates a post, each of their followers shall receive one `new_post` notification referencing the post and the author. | M |
| FR-NOTIF-03 | A user shall be able to list their own notifications, newest first, cursor-paginated, optionally only unread ones. | M |
| FR-NOTIF-04 | A user shall be able to get their unread notification count. | M |
| FR-NOTIF-05 | A user shall be able to mark one notification, or all notifications, as read. | M |
| FR-NOTIF-06 | A user shall be able to delete their own notifications. | M |
| FR-NOTIF-07 | A user shall never be able to read or change another user's notifications (`404`). | M |
| FR-NOTIF-08 | A failure while creating notifications shall not fail the request that triggered it. | M |

### 5.6 Platform (FR-PLAT)

| ID | Requirement | Priority |
|---|---|---|
| FR-PLAT-01 | The API shall be served under `/api/v1`. | M |
| FR-PLAT-02 | The system shall return all errors in one JSON format (`statusCode`, `error`, `message`, `path`, `timestamp`). | M |
| FR-PLAT-03 | The system shall reject unknown or invalid request fields with `400`. | M |
| FR-PLAT-04 | List endpoints shall use cursor pagination with `limit` (1 to 50, default 20) and return `data`, `nextCursor`, `hasMore`. | M |
| FR-PLAT-05 | The system shall provide Swagger documentation at `/docs` with Bearer authorization and the raw OpenAPI document at `/docs-json`. | M |
| FR-PLAT-06 | Swagger shall be disableable by configuration. | S |
| FR-PLAT-07 | The system shall refuse to start when required environment variables are missing. | M |
| FR-PLAT-08 | Responses shall never contain `passwordHash`, `imagePublicId` or `avatarPublicId`. | M |

### 5.7 Data migration (FR-MIG)

| ID | Requirement | Priority |
|---|---|---|
| FR-MIG-01 | The system shall provide a script to import Supabase users, profiles, posts, followers and notifications into PostgreSQL via Prisma, keeping the original UUIDs and dropping self-follows. | M |
| FR-MIG-02 | The system shall provide a script to recompute follower and following counters. | M |
| FR-MIG-03 | The system shall provide a resumable script to move existing images to Cloudinary and fill public IDs. | M |

## 6. External interface requirements

### 6.1 Client interface (REST)

- Protocol: HTTP/1.1 over TLS in production.
- Base path: `/api/v1`.
- Content types: `application/json`; `multipart/form-data` for uploads.
- Upload field names: `image` (posts), `file` (avatar).
- Authentication: `Authorization: Bearer <accessToken>`.
- Full endpoint contract: `news_share_api_design.md`.

### 6.2 Database interface

- PostgreSQL 16 via Prisma 6.
- Connection string from `DATABASE_URL`.
- Schema and migrations managed by Prisma only.

### 6.3 Cloudinary interface

- Cloudinary Node SDK (`cloudinary` v2), authenticated by cloud name, API key and API secret from environment variables.
- Operations: stream upload, destroy (delete) with CDN invalidation.
- Folder layout: `news_share/avatars/{userId}` and `news_share/posts/{userId}/{uuid}`.

### 6.4 Environment variables

| Variable | Required | Purpose |
|---|---|---|
| `NODE_ENV` | no | `development` or `production` |
| `PORT` | no | HTTP port (default 3000) |
| `DATABASE_URL` | yes | PostgreSQL connection string |
| `JWT_ACCESS_SECRET` | yes | Signing secret for access tokens |
| `JWT_ACCESS_TTL_SECONDS` | no | Default 900 |
| `JWT_REFRESH_TTL_DAYS` | no | Default 30 |
| `CLOUDINARY_CLOUD_NAME` | yes | Cloudinary account |
| `CLOUDINARY_API_KEY` | yes | Cloudinary key |
| `CLOUDINARY_API_SECRET` | yes | Cloudinary secret (server only) |
| `CLOUDINARY_ROOT_FOLDER` | no | Default `news_share` |
| `SWAGGER_ENABLED` | no | `false` disables `/docs` |

## 7. Data requirements

Full details are in `news_share_database_design.md`. Summary:

| Table | Purpose | Key constraints |
|---|---|---|
| `users` | Login identity | Unique email (lowercase) |
| `refresh_tokens` | Refresh token records | Unique token hash; cascade on user delete |
| `profiles` | Public profile; `id` equals `users.id` | Unique username; stores `avatar_url`, `avatar_public_id`, counters |
| `posts` | Posts | FK to profile (cascade); stores `image_url`, `image_public_id` |
| `followers` | Follow graph | Composite PK (`follower_id`, `following_id`) |
| `notifications` | In-app notifications | FK to recipient (cascade), actor (set null), post (cascade) |

Data rules:

- IDs are UUIDs; timestamps are `timestamptz`.
- The database stores image URLs and Cloudinary public IDs only.
- Usernames and emails are unique case-insensitively (enforced in services plus database unique indexes).
- Counters are denormalized and maintained inside transactions; a reconcile script repairs drift.
- Deleting a profile cascades to posts, follows and notifications. Cloudinary assets and other users' counters must be handled by the service before such a delete.

## 8. Non-functional requirements

### 8.1 Security (NFR-SEC)

| ID | Requirement |
|---|---|
| NFR-SEC-01 | Passwords hashed with argon2id; refresh tokens stored as SHA-256 hashes. |
| NFR-SEC-02 | Access tokens signed with a secret of at least 32 random bytes; secrets only in environment variables. |
| NFR-SEC-03 | The acting user id is taken only from the verified JWT, never from request data. |
| NFR-SEC-04 | Ownership is checked in services for every write (posts, profile, notifications, follows). |
| NFR-SEC-05 | Uploads validated for MIME type and size on the server; generated filenames only; client filenames ignored. |
| NFR-SEC-06 | `helmet` enabled; CORS restricted to known origins in production. |
| NFR-SEC-07 | Cloudinary API secret never sent to clients. |
| NFR-SEC-08 | Global rate limiting; stricter limits on register and login. |
| NFR-SEC-09 | Swagger disabled or password-protected in production. |

### 8.2 Performance (NFR-PERF)

| ID | Requirement |
|---|---|
| NFR-PERF-01 | List endpoints use indexed queries and cursor pagination (no offset scans). |
| NFR-PERF-02 | Typical read endpoints respond in under 300 ms (excluding image bytes) on a development machine with the sample dataset. |
| NFR-PERF-03 | Image bytes are served by the Cloudinary CDN, not by the API. |
| NFR-PERF-04 | Notification fan-out for a post shall not block the post-creation response. |

### 8.3 Reliability and data integrity (NFR-REL)

| ID | Requirement |
|---|---|
| NFR-REL-01 | Multi-step writes (register, follow, unfollow) run in transactions. |
| NFR-REL-02 | Cloudinary and database changes are ordered so a failure never leaves a row pointing at a missing image: upload then save; delete the row then the asset. |
| NFR-REL-03 | Failed Cloudinary deletions are logged and do not fail user requests. |
| NFR-REL-04 | Database backups can be produced with `pg_dump` and restored. |

### 8.4 Maintainability (NFR-MAINT)

| ID | Requirement |
|---|---|
| NFR-MAINT-01 | One module per feature; controllers thin, services hold business rules. |
| NFR-MAINT-02 | The Prisma schema is the only definition of the database; migrations are committed. |
| NFR-MAINT-03 | TypeScript strictness and lint rules enforced in CI. |
| NFR-MAINT-04 | DTO classes carry all validation; Swagger documents them automatically through the CLI plugin. |
| NFR-MAINT-05 | Storage and database access are isolated behind `StorageService` and `PrismaService` so either can be replaced. |

### 8.5 Portability and operability (NFR-OPS)

| ID | Requirement |
|---|---|
| NFR-OPS-01 | Local development requires only Node.js, Docker and a Cloudinary account. |
| NFR-OPS-02 | All configuration comes from environment variables, validated at startup. |
| NFR-OPS-03 | Production deploys apply migrations with `prisma migrate deploy`. |
| NFR-OPS-04 | Errors are logged server-side; clients never receive stack traces. |

### 8.6 Usability for API consumers (NFR-USE)

| ID | Requirement |
|---|---|
| NFR-USE-01 | Interactive documentation lets a developer log in, authorize and call every endpoint. |
| NFR-USE-02 | Error messages are specific enough to display to end users (validation errors list each field). |
| NFR-USE-03 | Field names are consistent camelCase; timestamps ISO 8601 UTC. |

### 8.7 Testability (NFR-TEST)

| ID | Requirement |
|---|---|
| NFR-TEST-01 | End-to-end tests run against a separate test database. |
| NFR-TEST-02 | `StorageService` can be mocked so tests never call Cloudinary. |
| NFR-TEST-03 | Tests cover authentication, ownership rules, follow idempotence and counters, and notification isolation. |

## 9. NestJS implementation examples

The snippets below show the patterns every module follows. Full code is in `news_share_implementation_steps.md`.

### 9.1 Bootstrap: `src/main.ts` (FR-PLAT-01, 02, 03, 05, 06)

```ts
import { ValidationPipe } from '@nestjs/common';
import { NestFactory } from '@nestjs/core';
import helmet from 'helmet';
import { AppModule } from './app.module';
import { AllExceptionsFilter } from './common/filters/all-exceptions.filter';
import { setupSwagger } from './common/swagger/setup-swagger';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.setGlobalPrefix('api/v1');
  app.use(helmet());
  app.enableCors();
  app.useGlobalPipes(
    new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true }),
  );
  app.useGlobalFilters(new AllExceptionsFilter());

  if (process.env.SWAGGER_ENABLED !== 'false') setupSwagger(app);

  await app.listen(process.env.PORT ?? 3000, '0.0.0.0');
}
```

### 9.7 Service with a transaction and ownership check (FR-FOLLOW-01 to 04, FR-POST-10)

```ts
// follows.service.ts: idempotent follow with counters in one transaction
async follow(me: string, targetId: string) {
  if (me === targetId) throw new BadRequestException('Cannot follow yourself');

  const target = await this.prisma.profile.findUnique({ where: { id: targetId }, select: { id: true } });
  if (!target) throw new NotFoundException('User not found');

  const created = await this.prisma.$transaction(async (tx) => {
    const res = await tx.follow.createMany({
      data: [{ followerId: me, followingId: targetId }],
      skipDuplicates: true,
    });
    if (res.count === 1) {
      await tx.profile.update({ where: { id: me }, data: { followingCount: { increment: 1 } } });
      await tx.profile.update({ where: { id: targetId }, data: { followersCount: { increment: 1 } } });
    }
    return res.count === 1;
  });

  if (created) this.events.emit(EVENTS.USER_FOLLOWED, new UserFollowedEvent(me, targetId));
  return { following: true };
}
```

```ts
// posts.service.ts: upload first, undo the upload if the database write fails (FR-POST-04)
async create(userId: string, dto: CreatePostDto, image?: Express.Multer.File) {
  if (!dto.title && !dto.content && !image) {
    throw new BadRequestException('A post needs a title, content or an image');
  }
  const upload = image ? await this.storage.uploadPostImage(userId, image) : null;
  try {
    const post = await this.prisma.post.create({
      data: { userId, title: dto.title, content: dto.content,
              imageUrl: upload?.url, imagePublicId: upload?.publicId },
      include: { author: { select: AUTHOR_SELECT } },
    });
    this.events.emit(EVENTS.POST_CREATED, new PostCreatedEvent(post.id, userId));
    return this.toResponse(post);           // imagePublicId is not included
  } catch (err) {
    await this.storage.safeDelete(upload?.publicId);
    throw err;
  }
}
```

### 9.9 Event listener (FR-NOTIF-01, 02, 08)

```ts
@Injectable()
export class NotificationListener {
  private readonly logger = new Logger(NotificationListener.name);
  constructor(private readonly prisma: PrismaService) {}

  @OnEvent(EVENTS.POST_CREATED, { async: true })
  async onPostCreated(e: PostCreatedEvent) {
    try {
      const followers = await this.prisma.follow.findMany({
        where: { followingId: e.authorId },
        select: { followerId: true },
      });
      if (!followers.length) return;
      await this.prisma.notification.createMany({
        data: followers.map((f) => ({
          userId: f.followerId, actorId: e.authorId, type: 'new_post',
          postId: e.postId, message: 'A user you follow posted something new!',
        })),
      });
    } catch (err) {
      this.logger.error(`new_post notifications failed: ${(err as Error).message}`); // never fails the request
    }
  }
}
```

### 9.12 Cursor pagination helper (FR-PLAT-04)

```ts
export const cursorArgs = (cursor?: string) => (cursor ? { cursor: { id: cursor }, skip: 1 } : {});

export function toPage<T extends { id: string }, R>(rows: T[], limit: number, map: (row: T) => R) {
  const hasMore = rows.length > limit;          // rows were fetched with take: limit + 1
  const items = hasMore ? rows.slice(0, limit) : rows;
  return { data: items.map(map), nextCursor: hasMore ? items[items.length - 1].id : null, hasMore };
}
```

### 10.1 Technology dependencies

| Component | Version / note |
|---|---|
| Node.js | 20 or newer |
| NestJS | Current stable (`@nestjs/common`, `core`, `platform-express`, `config`, `jwt`, `passport`, `swagger`, `event-emitter`, `throttler`) |
| Prisma | 6 (`prisma@6`, `@prisma/client@6`); a newer major version needs a different setup (`prisma.config.ts`, driver adapter) |
| PostgreSQL | 16 (13+ works: `gen_random_uuid()` is built in) |
| Cloudinary | `cloudinary` Node SDK v2 |
| Hashing | `argon2`, `bcryptjs` (legacy hashes only) |
| Validation | `class-validator`, `class-transformer` |
| Uploads | `multer` via `@nestjs/platform-express` |
| Security | `helmet`, `@nestjs/throttler` |

### 10.2 Risks

| Risk | Mitigation |
|---|---|
| Imported Supabase bcrypt hashes may not verify | Test one real account first; fall back to a password-reset flow |
| Old Supabase image URLs are private or expire | Download then upload buffers instead of remote fetch |
| Counters drift after bulk operations | Run `reconcile-follow-counts.ts` |
| Fan-out slows down for accounts with huge follower counts | Move notification creation to a queue (BullMQ) |
| Cloudinary outage | Post creation without an image keeps working; uploads return `500` and nothing partial is saved |
| Account deletion leaves Cloudinary files or stale counters | Not exposed in v1; if added, delete assets and adjust counters first |

## 11. Acceptance criteria

The system is accepted when all of the following pass.

### 11.1 Authentication
- [ ] AC-01: Registering returns `201` with `profile`, `accessToken`, `refreshToken` and no `passwordHash`. (FR-AUTH-01, 04)
- [ ] AC-02: Registering with an existing email or username (any letter case) returns `409`. (FR-AUTH-02)
- [ ] AC-03: A username like `ab` or `a b!` returns `400`. (FR-AUTH-03)
- [ ] AC-04: Wrong email and wrong password both return `401` with the same message. (FR-AUTH-06)
- [ ] AC-05: Refreshing returns a new pair; reusing the old refresh token returns `401`. (FR-AUTH-07)
- [ ] AC-06: Any non-auth endpoint without a token returns `401`. (FR-AUTH-11)
- [ ] AC-07: An imported account with a bcrypt hash can log in and its stored hash becomes argon2id. (FR-AUTH-10)

### 11.2 Profiles
- [ ] AC-08: `GET /me` includes email; `GET /users/:id` does not. (FR-USER-01, 03)
- [ ] AC-09: Changing to a taken username returns `409`. (FR-USER-02)
- [ ] AC-10: Uploading an avatar returns a `res.cloudinary.com` URL and the asset exists in Cloudinary; a `.txt` upload returns `400`. (FR-USER-05)

### 11.3 Posts
- [ ] AC-11: A post with no title, content or image returns `400`. (FR-POST-01)
- [ ] AC-12: A post with an image returns `imageUrl` on `res.cloudinary.com`; the JSON contains no `imagePublicId`; the database row has it. (FR-POST-03, FR-PLAT-08)
- [ ] AC-13: A user cannot update or delete another user's post (`403`). (FR-POST-09, 10)
- [ ] AC-14: Replacing a post image deletes the old Cloudinary asset. (FR-POST-09)
- [ ] AC-15: Deleting a post removes the row and the Cloudinary asset. (FR-POST-10)
- [ ] AC-16: The feed shows posts from followed users and the user's own, newest first; page 2 via `nextCursor` has no duplicates or gaps. (FR-POST-06, FR-PLAT-04)

### 11.4 Follows and notifications
- [ ] AC-17: Following yourself returns `400`; following twice leaves counters at `+1` and creates one notification. (FR-FOLLOW-01, 02, 07)
- [ ] AC-18: Unfollowing decrements both counters once; unfollowing again changes nothing. (FR-FOLLOW-04)
- [ ] AC-19: After a follow, the target has one `follow` notification; after the followee posts, each follower has one `new_post` notification. (FR-FOLLOW-07, FR-NOTIF-02)
- [ ] AC-20: A user marking another user's notification as read gets `404` and nothing changes. (FR-NOTIF-07)
- [ ] AC-21: `unread-count` matches the number of unread items; `read-all` sets it to `0`. (FR-NOTIF-04, 05)

### 11.5 Platform
- [ ] AC-22: Every error body has `statusCode`, `error`, `message`, `path`, `timestamp`. (FR-PLAT-02)
- [ ] AC-23: Sending an unknown field returns `400`. (FR-PLAT-03)
- [ ] AC-24: `/docs` lists all tags; **Authorize** with a login token makes protected calls succeed. (FR-PLAT-05)
- [ ] AC-25: Starting the server without `DATABASE_URL` fails with a clear message. (FR-PLAT-07)
- [ ] AC-26: The import scripts load a sample export, counters match actual follow rows after reconcile, and migrated image URLs open from Cloudinary. (FR-MIG-01 to 03)
- [ ] AC-27: The e2e test suite passes against the test database with Cloudinary mocked. (NFR-TEST-01 to 03)

## 13. Out of scope and future work

Not part of version 1:

- Likes, comments, reposts, hashtags, post search.
- Email verification, password reset, social login, two-factor authentication.
- Account deletion and data export.
- Private accounts, blocking, reporting, moderation tools, admin role.
- Push notifications and real-time delivery (WebSocket or SSE).
- Video or non-image attachments.
- Per-user precomputed feeds and queue-based fan-out (planned if scale requires).

## 14. Glossary

| Term | Meaning |
|---|---|
| Access token | Short-lived JWT proving the caller's identity |
| Refresh token | Long-lived opaque token exchanged for a new token pair; rotated on use |
| Cloudinary | External image hosting and CDN service |
| Public ID | Cloudinary's identifier for an asset, needed to replace or delete it |
| Cursor pagination | Paging by "items after this id" instead of page numbers |
| DTO | Data Transfer Object: a class that validates and documents request data |
| Fan-out | Creating one notification per follower when a user posts |
| Prisma | TypeScript ORM and migration tool used for PostgreSQL access |
| RLS | Row Level Security, the Supabase mechanism replaced by service-level checks |
| SRS | Software Requirements Specification (this document) |
| Swagger / OpenAPI | Interactive API documentation and its machine-readable specification |
